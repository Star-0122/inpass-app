# KOTCO（INPASS）

イベントを探す・見る・参加する・チケットを取得する・QRコードで入場するまでを
一つにまとめたイベントプラットフォームです。日本語・英語の2言語に対応しています。

## 動作モード

| モード | 条件 | データの保存先 | 複数端末での同期 |
|---|---|---|---|
| **ローカルモード**（既定） | `supabaseConfig` が未設定のとき | このブラウザの `localStorage` のみ | ❌ されません |
| **クラウドモード** | `supabaseConfig` にSupabaseプロジェクトの情報を設定したとき | Supabase（Postgres + Auth + Storage + Realtime） | ✅ されます |

`index.html` 先頭付近の `supabaseConfig` を書き換えるだけで自動的にモードが切り替わります。

```
index.html      … アプリ本体（UI・ロジックすべて含む単一ファイル）
schema.sql       … Supabase用のテーブル・RLS・RPC関数・Storageバケット定義
manifest.json    … PWAマニフェスト
sw.js            … Service Worker（バージョン管理つき）
icons/           … アプリアイコン
```

## 1. GitHub Pagesへのデプロイ

このアプリはすべて相対パスで構成されており、`https://<ユーザー名>.github.io/<リポジトリ名>/`
のようなサブパス配下でもそのまま動作します。

1. このフォルダの中身（`index.html`・`schema.sql`・`manifest.json`・`sw.js`・`icons/`）を
   リポジトリのルート（または `docs/` など公開ディレクトリ）にそのまま配置する
2. GitHub の Settings → Pages で公開ブランチ／ディレクトリを設定する
3. HTTPS配信になるため、QRカメラ機能もそのまま利用できます（カメラはHTTPS必須です）

### Service Workerのキャッシュ更新について
新しいバージョンを公開するときは、`sw.js` 内の `CACHE_NAME` を必ず更新してください
（例：`inpass-v2` → `inpass-v3`）。更新しないと、古いHTML/JSがブラウザに
キャッシュされたままになり、修正が反映されないことがあります。

## 2. クラウドモードのセットアップ（複数端末での同期・サーバー側の権限チェックを使う場合）

### 2-1. Supabaseプロジェクトを作成
1. https://supabase.com/ でアカウントを作成し、新規プロジェクトを作成
2. 「Settings → API」から **Project URL** と **anon public key** をコピー
   （**Service Role Key はフロントエンドに絶対に書かないでください**）

### 2-2. データベースを構築
Supabaseダッシュボードの「SQL Editor」を開き、`schema.sql` の中身をすべて貼り付けて実行してください。
テーブル・RLS（行単位アクセス制御）・トリガー・RPC関数・Storageバケット（`event-photos`・`avatars`）が
すべて作成されます。

### 2-3. アプリに接続情報を設定
`index.html` 内の以下を書き換えてください（公開しても問題ない値です。実際のアクセス制御は
`schema.sql` のRLSとRPC関数が行います）。

```js
const supabaseConfig = {
  url: "YOUR_SUPABASE_URL",
  anonKey: "YOUR_SUPABASE_ANON_KEY",
};
```

### 2-4. 最初の管理者アカウントを作る
1. アプリから通常のユーザーとして1人分、新規登録する
2. Supabaseダッシュボード → Table Editor → `profiles` テーブルを開く
3. そのユーザーの `role` を `admin` に書き換えて保存する
4. 以降、主催者・スタッフへの権限付与は、その管理者アカウントでログインした状態で
   ブラウザの開発者ツールのコンソールから次のように実行してください（現時点では
   管理者向けのUI画面は未実装です）。

```js
await sb.rpc('admin_set_role', { p_target: '対象ユーザーのUID', p_role: 'organizer' });
```

### 2-5. スタッフの割り当て
主催者が「主催者管理画面 → スタッフ管理」から、スタッフ役のメールアドレスを
入力してイベント担当に追加できます（相手が先にKOTCOへ新規登録している必要があります）。

## 3. アプリモードの切り替え（ユーザー／主催者／スタッフ）

画面上部に常時表示される切り替えボタンは廃止し、「メニュー → アプリモード」から
切り替える方式にしました。

- 実際に主催者・スタッフの権限（Supabase側のrole、またはローカル版のロール）を
  持っている場合は、パスワードなしでそのまま切り替わります。
- 権限を持っていない場合は、動作確認用として **パスワード `7852`** を入力すると
  一時的に（このセッション内のみ）該当モードの画面をプレビューできます。
  これは本番の権限管理ではなく、あくまで開発・テスト用の簡易な仕組みです。
  本番運用では、上記2-4のとおりSupabaseのroleベースで権限を付与してください。

## 4. QRコード・カメラについて

- チケット取得時に、実際にスマートフォンのカメラで読み取れるQRコードを生成します
  （ペイロードは `INPASS1:チケットコード:イベントID` のみで、個人情報は含みません）。
- スタッフ画面の「QRを読み取る」は、以下の順で状態を確認してから起動します。
  1. HTTPS（安全な接続）かどうか
  2. `navigator.mediaDevices.getUserMedia` が利用可能か
  3. QRコード読み取りライブラリ（jsQR）が読み込まれているか
  4. カメラへのアクセス許可が得られるか
  5. 使用できるカメラが存在するか
  それぞれの段階で失敗した場合、原因に応じた日本語・英語のメッセージを表示し、
  「🔄 カメラを再試行」ボタンと、チケットID手入力による代替手段を必ず提供します。
- 複数のカメラがある端末では、カメラを選択するプルダウンが表示されます
  （スマートフォンでは背面カメラを優先します）。
- QR読み取り画面を閉じる・スタッフモードを終了する・ページを非表示にする・
  ページを離れる、のいずれの場合もカメラストリームを確実に停止します。

### クラウドモードでの二重チェックイン防止
チェックインはPostgresの `check_in_ticket()` 関数（`SECURITY DEFINER`）内で
`SELECT ... FOR UPDATE` による行ロックを使って処理されるため、同じチケットを
複数端末からほぼ同時に読み取っても、必ず一方だけが「入場OK」、もう一方は
「使用済み」と判定されます（ブラウザのlocalStorageだけに頼っていません）。

## 5. 日本語・英語の切り替え

「メニュー → Language / 言語」から切り替えられます。設定は `localStorage` に
保存され、次回アクセス時にも維持されます。ナビゲーション・主要な画面タイトル・
QRカメラのエラーメッセージ・チェックイン結果など、ユーザーが直接操作する
主要なUIを翻訳しています。イベントの説明文や管理画面の詳細な項目名など、
主催者向けの一部コンテンツは現時点では日本語のみです。

## 6. セキュリティ設計（クラウドモード）

| 要件 | 実装方法 |
|---|---|
| ユーザーは自分のチケット・お気に入りしか見られない | Row Level Security（`tickets`・`favorites`テーブル） |
| 主催者は自分のイベントしか編集できない | RLSポリシーで `organizer_id = auth.uid()` を必須化 |
| スタッフは担当イベントのチケットしかチェックインできない | `check_in_ticket()` 関数内で `staff_assignments` テーブルを確認 |
| チケットの状態はクライアントから直接書き換えられない | `tickets` テーブルにUPDATE用ポリシーを設定せず、関数経由のみ許可 |
| 同じチケットの二重チェックインを防ぐ | 行ロック（`FOR UPDATE`）による排他制御 |
| ユーザーが自分の権限（role）を書き換えられない | トリガーで自己変更をブロック。`admin_set_role()` 関数経由のみ変更可 |
| 1ユーザーが同じイベントのチケットを複数回取得できない | `UNIQUE(event_id, user_id)` 制約 |
| 個人情報がQRコードに含まれない | ペイロードは `INPASS1:チケットコード:イベントID` のみ |
| プロフィール画像は本人のフォルダにのみアップロード可 | Storageポリシーで `auth.uid()` とフォルダ名を照合 |
| Service Role Keyをフロントエンドに書かない | anon keyのみを使用し、権限はRLS/RPCで制御 |

## 7. 正直な制約

- **アカウント削除（退会）**：プロフィール・お気に入り・チケットは削除されますが、
  `auth.users` 自体の完全な削除にはSupabaseのService Role Keyを使うサーバー処理
  （Edge Functionなど）が別途必要です。
- **管理者向けのロール変更UI**：現時点ではブラウザのコンソールから直接RPCを
  呼ぶ運用です。
- **プッシュ通知**：アプリを閉じている間の本物のプッシュ配信（FCM/APNs相当）は
  未実装です。アプリを開いている間の「テスト通知」のみ対応しています。
- **エラーハンドリング**：主要な操作は try/catch で保護し、失敗時も画面が
  真っ白にならないようにしていますが、すべての組み合わせを網羅したテストは
  行っていません。

## 10. 今回の修正内容（下部ナビ固定・Liquid Glass・QR安定化・モード認証）

### 変更したファイル
- `index.html`（CSS・JavaScriptともに修正）
- `sw.js`（キャッシュバージョンを `inpass-v3` に更新、vendor内のQRライブラリも事前キャッシュ対象に追加）
- `vendor/jsQR.js`（新規追加：QR読み取りライブラリをnpm公式パッケージからそのまま同梱）
- `vendor/qrcode.js`（新規追加：QRコード生成ライブラリをnpm公式パッケージからそのまま同梱）

### ① 下部ナビゲーションが表示されない問題の原因と修正
**原因**：`.phone-shell`（アプリ全体を囲む要素）が `min-height:100vh` だけを指定しており、
実際の高さ（`height`）を固定していませんでした。そのため、中身が多い画面では
`.phone-shell` 自体がビューポートより縦に伸びてしまい、内部の `.screen` が
「はみ出た分だけページ全体をスクロールしないと見えない」状態になり、
`position:absolute` で配置していた下部ナビも一緒に画面外へ押し出されていました。

**修正**：`.phone-shell` に `height:100vh`（`100dvh` も指定し、モバイルブラウザの
アドレスバー分のズレにも対応）を設定し、常にビューポートぴったりの高さに固定。
これにより内部の `.screen` だけが正しくスクロールするようになり、下部ナビは
最初から・常に画面下部に表示されます。`.screen` の `padding-bottom` も
`calc(92px + env(safe-area-inset-bottom))` として、iPhoneのSafe Area分を含めて
コンテンツがナビの裏に隠れないようにしました。

### ② iPhone限定のLiquid Glass風デザイン
`navigator.userAgent` を使って「iPhone / iPod（かつiPadではない、iPadOS 13+がMacと
偽装しているケースも除外）」を判定し、該当する場合のみ `<html>` に `iphone` クラスを
付与。CSSは `@supports (backdrop-filter: blur(1px))` で対応ブラウザだけに、
`html.iphone .bottom-nav` というスコープで半透明・ぼかし背景・上部角丸・
タップ時の縮小フィードバックを適用しています。Android・PC・iPadでは
このクラスが付かないため、既存のデザインがそのまま維持されます。

### ③ QRコード読み取りエラーの根本原因と修正
**原因**：QR生成・読み取りライブラリを外部CDN（cdnjs）から都度ダウンロードする
構成になっており、CDNへの接続が失敗する・遅い・ブロックされる環境では
ライブラリが読み込めず、エラーメッセージが表示されていました。

**修正**：
1. `jsQR`（読み取り用）と `qrcode-generator`（生成用）を、npm公式パッケージから
   取得したファイルをそのまま `vendor/jsQR.js` / `vendor/qrcode.js` としてアプリに
   同梱し、外部CDNに一切依存せずに動作するようにしました。
2. 万一 `vendor/` 内のファイル自体が見つからない場合（配置忘れなど）に限り、
   CDNからの読み込みを緊急フォールバックとして試みます。
3. QRの読み取り方式に、ブラウザ内蔵の **BarcodeDetector API**（追加ライブラリ
   不要・対応ブラウザではより高速）を最優先で使用し、非対応ブラウザでは
   同梱の `jsQR` にフォールバックする2段構成にしました。
4. カメラの起動可否は「HTTPS→API存在→ライブラリ読み込み→権限→カメラ有無」の
   順に個別診断し、原因に応じた日本語メッセージ＋「🔄カメラを再試行」ボタン、
   さらにチケットID手入力への切り替えを常に提供します。

### ④⑤ 主催者・スタッフモードへの認証
「メニュー → アプリモード」から主催者・スタッフを選択すると、実際の権限の
有無にかかわらず必ずパスワード入力画面（「◯◯モードへ切り替えます」
「パスワードを入力してください」）を経由するようにしました。開発・確認用の
パスワードは `DEV_MODE_PASSWORD`（値：`7852`）としてコード内に明示的に分離し、
「これは本番の権限管理ではない」という注意コメントを付けています。
**実際のデータ操作（イベント編集・チェックインなど）の可否は、このパスワードとは
完全に独立して、Supabase側のRLS・RPC関数がサーバー側で判定します。** パスワードを
知っているだけでは、本物の主催者・スタッフ権限は一切付与されません。

### ⑥ 「ユーザーに戻る」ボタン
主催者画面の右上、およびスタッフ画面の戻るボタンから、「ユーザーモードに
戻りますか？」の確認ダイアログ（キャンセル／戻る）を経由してユーザーモードの
ホーム画面へ戻れるようにしました。

### エラーメッセージについて
Supabaseから返る英語のエラーメッセージをそのままユーザーに表示しないよう、
`friendlyError()` 関数のフォールバック文言を「データを取得できませんでした。
通信環境を確認して、もう一度お試しください。」という日本語の汎用メッセージに
統一しました（技術的な詳細はconsole.errorにのみ出力）。
